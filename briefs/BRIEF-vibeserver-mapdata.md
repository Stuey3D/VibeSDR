# VibeServer serves the bundled map — `/mapdata/v1/…`

2026-09-26. The vector map dataset built today (`assets/mapdata/v1`, generated by
`scripts/gen-map-data.mjs`) now reaches a browser from `vibeserver` itself, so a receiver draws its
own coastlines with no outbound internet and no OpenStreetMap tiles. Nothing here is deployed: the
work is in the tree for review.

## 1. What a listener sees

`GET /mapdata/v1/<file>` — the flat filenames the generator emits, served from disk. The web client
already asks for exactly that path (`MAP_DATA_BASE = '/mapdata/v1/'` in `src/components/MapOverlay.tsx`,
`MD` in `directory/public/index.html`), root-relative, so the phone app's WebView — pointed at the
server's origin — and a plain browser get the same data from the server being listened to. A local
dongle is a loopback VibeServer, so it works offline too.

## 2. Files on disk, never compiled in

`android/app/src/main/cpp/vibe_mapdata.h` is the whole serving path (~190 lines, header-only,
included by `local_sdr_shim.cpp`). The rule the header exists to enforce: the basic pack is ~22 MB
and the detail pack ~221 MB, and the base64-in-the-binary trick every other asset here uses
(`vibe_web_page.h`) would make that resident for the life of the process. A Pi 2 has 1 GB for the
whole machine. So: `stat()` for the length, `fopen`, 64 KB chunks through `Socket::send`, nothing
held.

Decisions worth knowing:

- **Where the data is found**, in order: `VIBESERVER_MAPDATA_DIR`, then `<exe>/../lib/vibeserver/mapdata`
  (the `.deb` layout, and the same "wherever we are unpacked" relation as the bundled librtlsdr's
  RPATH), `<exe>/mapdata`, `/usr/lib/vibeserver/mapdata`, `/usr/share/vibeserver/mapdata`,
  `/var/lib/vibeserver/mapdata`. Resolved once and cached — a map load asks for ~160 files and a
  four-directory `stat()` storm per request is a real cost on a Pi.
- **Absent is degraded, not broken.** No directory ⇒ every request is a clean 404 and the server
  runs exactly as before. The two 404 bodies differ on purpose: *no map data installed* (nothing
  there) versus *this server does not carry that map layer — the optional detail pack may not be
  installed*. One message for both is how "install the optional pack" gets read as a client bug.
- **Long cache, honestly.** `Cache-Control: public, max-age=31536000, immutable`. Safe only because
  the path names the dataset version, so the bytes at a URL never change — unlike the client and the
  favicon, which are deliberately short-lived because they change with the server.
- **Traversal** is refused by an allow-list on the filename (letters, digits, `.`, `-`, `_`; no
  leading dot, no `..`, nothing containing `/`) *before* a path is built. The dataset is one flat
  directory, so that costs nothing.
- **`HEAD` is answered** as well as `GET`, so a client can ask whether a server has the detail pack
  without downloading a shard.
- **Optional pre-compressed siblings.** If `<file>.gz` exists beside a file and the client sent
  `Accept-Encoding: gzip`, that is what goes out with `Content-Encoding: gzip`. We never gzip on the
  fly — a deflate of a 20 MB file on a connection thread on a Pi, for a file that never changes, is
  the wrong trade. The packages ship the files raw; an owner tight on disk can `gzip -k` the tree and
  the server picks it up with no configuration.
- **The front door serves it too** (added to the `frontDoorOnly` allow-list in
  `local_sdr_shim.cpp`). The landing page draws the same map; refusing it there would give every
  multi-radio machine a blank map on its front page while each radio's page drew one perfectly.

The router reads one new request header (`Accept-Encoding`) alongside the ones it already collects.

## 3. Packaging

**Basic pack → inside `vibeserver`** (`vibeserver/CMakeLists.txt`, the Linux block). The file list is
read from `assets/mapdata/v1/index.json` with CMake's `string(JSON …)` — never a list in the build
file and never a glob. The data is generated and its shape changes (shards appear, the relief became
tiles today), and a hand-copied list ships a package that installs cleanly and is missing a layer,
which reads as a renderer bug. Installed to `lib/vibeserver/mapdata`; 27 files today (26 declared +
`index.json`, which is the manifest of *both* packs and therefore belongs with the server).

A tree with no usable map data is a **`FATAL_ERROR`**, with `-DVIBESERVER_ALLOW_NO_MAPDATA=ON` as the
named escape hatch. This is the cloudflared lesson applied before it bites: a package built without
the files does not merely lack them, it *deletes* the copy on every machine that upgrades, and the
server keeps serving radio perfectly while the map goes blank.

`project(vibeserver VERSION …)` bumped **5.6.54 → 5.6.55** — an unbumped version is a silent no-op
install.

**Detail pack → its own package**, `vibeserver-mapdata-detail`, built by
`scripts/build-mapdata-deb.sh`. `Architecture: all` (it is GeoJSON and PNG — one package for arm64,
armhf and amd64, which is the only reason 65 MB in the pool is tolerable), `Depends: vibeserver`,
and `vibeserver` now carries `Recommends: ffmpeg, vibeserver-mapdata-detail`. Recommends, never
Depends: apt installs and upgrades Recommends by default, while `--no-install-recommends` or a Pi on
a 4 GB card simply gets the basic map and a working receiver. Version is
`<index version>.<generation date>-<rev>` (today `1.20260926-1`), so regenerating the data on a later
day bumps itself; regenerating twice in one day needs `--rev 2`.

The script stages from `index.json`'s own pack list, refuses if a declared file is absent, writes a
`copyright` generated from `index.json`'s `licences` block (part of the data is CC BY 4.0 —
attribution is a condition of redistribution, the same point the CMake file makes about cloudflared),
and then **counts the files inside the finished `.deb`** and fails if that disagrees with the
manifest. A staged tree that copied nothing produces a perfectly valid 4 KB package.

It needs `python3` (`jq` is not on a Debian image and `grep`-parsed JSON is how a layer goes missing),
so `vibeserver/linux/Dockerfile.build` now installs `python3-minimal`. **That invalidates the build
image's apt layer, so the next `publish-apt-docker.sh` run rebuilds the image — expect the extra
minutes.**

### How a server owner installs the detail pack

```
sudo apt update && sudo apt install vibeserver-mapdata-detail   # ~65 MB down, ~226 MB on disk
sudo apt remove vibeserver-mapdata-detail                      # back to the basic map, nothing else lost
```
On a fresh `apt install vibeserver` it arrives by itself (Recommends). No restart is needed — the
server opens these files per request, so the map fills in on the next page load.

### Publishing it

Not wired into `scripts/publish-apt.sh`, deliberately — that script is per-architecture and this
package is not, and it prunes on `vibeserver_*_$ARCH.deb` globs it would have to learn about. The
script prints the two manual steps: copy the `.deb` into `pool/main/v/vibeserver/` and re-run
`dpkg-scanpackages` **for every architecture** (an `Architecture: all` package appears in each
architecture's index), then re-sign `Release` as `publish-apt.sh` does. Doing it properly — teaching
the publish script about a data package, including pruning old dataset versions — is the obvious next
piece of work and is *not* done.

## 4. What was actually verified, and how

- `vibeserver_core` and the `vibeserver` binary **compile and link** with the new route, on this Mac
  (`cmake --build vibeserver/build`). **That is a macOS host compile, not a Linux or ARM build** — no
  claim is made about the Pi beyond what is below.
- **The serving path, over a real socket**, with a throwaway harness linking `net_shim.cpp` and
  `vibe_mapdata.h` (no radio, no server process, nothing touched): `index.json` served byte-exact
  (26,033 bytes), a 2.75 MB layer byte-for-byte identical to the file on disk, `image/png` for a
  relief tile, the `immutable` cache header, `Content-Encoding: gzip` + `Vary` when a `.gz` sibling
  exists and the client asked, `HEAD` returning headers only, a raw
  `GET /mapdata/v1/../../../etc/passwd` refused with the 404, and the two distinct 404 bodies.
- **Directory discovery, on Linux, in a bookworm container**: nothing installed ⇒ empty and
  `installed()` false; binary at `/usr/bin` with data at `/usr/lib/vibeserver/mapdata` (the `.deb`
  layout) found; the same tree staged under `/opt/vs` found exe-relative; `VIBESERVER_MAPDATA_DIR`
  winning over both.
- **CMake's `index.json` parsing**: 27 files, the right ones, run as a standalone `cmake -P` script
  (the install block is inside `if(UNIX AND NOT APPLE)` and does not execute on this Mac).
- **Both packages built for real** in a bookworm container: `vibeserver-mapdata-basic` (26 files,
  22.7 MB staged, 8.9 MB `.deb` — built only as a test of the machinery; it is not a release
  artefact, the basic pack ships inside `vibeserver`) and `vibeserver-mapdata-detail` (139 files,
  231.6 MB staged, **65 MB `.deb`**, `Installed-Size: 226508`). Control fields and the generated
  `copyright` inspected with `dpkg-deb`.
- Nothing was deployed, committed, pushed or published; no server was touched; the temporary build
  tree was deleted.

## 5. Not done / assumed

- **No full Linux or ARM build of `vibeserver` with these changes**, and no run on a Pi. The C++ is
  plain POSIX and was compiled by both clang (macOS) and g++ (bookworm, the discovery harness), but
  the ARM package has not been built.
- **macOS gets no map data.** `mac/build-app.sh` is untouched, so a `VibeServer.app` serves 404s for
  `/mapdata/…` unless `VIBESERVER_MAPDATA_DIR` is set by hand. Doing it properly means shipping the
  basic pack in the bundle's Resources and pointing `vibemap::setDir()` at it from `main.cpp` — the
  setter exists for exactly that and is currently called by nobody.
- **The phone app's own bundled copy** is untouched; this is the server side only.
- **`country-labels.json` is on disk but in neither pack**, so it ships in nothing. It is either dead
  or a generator omission — worth a word with whoever owns `gen-map-data.mjs`. (I did not modify the
  generator, the assets or `directory/public/index.html`, as instructed.)
- **The client asks for names the detail pack does not have.** `MapOverlay.tsx`'s tier-2 list fetches
  `tier2-lakes.json` and `tier2-admin1.json`, which are *sharded* on disk (`…s0.json` … `…s36.json`).
  The renderer agent is mid-flight on that; the server serves whatever is asked for and 404s the
  rest, which is why the 404 says what it says.
- **Assumed, not checked:** that the `packs` split in `index.json` is settled (my packaging reads it
  at build time, so it tracks whatever it becomes); and that `dpkg-scanpackages --arch <a>` includes
  `Architecture: all` packages in each index — standard behaviour, but the apt repository was not
  touched to prove it here.
