# 9600 packet (G3RUH), FX.25 and IL2P (V12)

Branch `v12-ax25hs` (from `v12-experimental`). The APRS decoder (docs/v12/AIS-APRS.md) becomes a **packet decoder**:
beside 1200 Bd AFSK and HF 300 Bd it now has **9600 Bd G3RUH** (terrestrial 9k6 on 2 m / 70 cm and many cubesats), and
on 1200 and 9600 it also reads **FX.25** (Reed-Solomon round an ordinary AX.25 frame) and **IL2P** (Reed-Solomon packet
radio without bit-stuffing). Every frame heard — APRS or not — goes into a **frame log** (hex and ASCII, the satellite's
name where its callsign gives it). APRS frames still make stations on the list and the map.

## Standards, and other people's code

Our own code, from the published documents:

- **G3RUH:** James Miller, "9600 Baud Packet Radio Modem Design" — direct FM by the shaped baseband, scrambler
  1 + x^12 + x^17 after NRZI, ±3 kHz deviation, a data slicer and a clock from the zero crossings.
- **AX.25 v2.2** (TAPR) and ISO 13239 HDLC (`vibe_hdlc.h`, shared with AIS / APRS).
- **FX.25:** Stensat Group, "FX.25 Forward Error Correction Extension to AX.25", draft 0.01.06 (2006): the frame, the
  LSb-first order, the tag table (the tag values are copied from it — facts), the pad.
- **IL2P:** Nino Carrillo KK4HEJ, "IL2P Specification Draft v0.6" (16 March 2024, tarpn.net): sync word, header map,
  PID and control tables, the LFSR schematics and initial states, payload block sizes, the trailing CRC and its Hamming
  tables (copied — facts), and the three example packets (our test vectors).
- **Facts the specs leave open** were taken from Dire Wolf's documentation and source (GPL — read for facts, nothing copied):
  FX.25's RS first root is 1 (field 0x11D); IL2P's first root is 0 (the spec says so too); IL2P is fed the RAW line bits,
  before the G3RUH descrambler and without NRZI; the pre-v0.6 baseline FEC (blocks ≤ 247, 2/4/6/8 check bytes for small
  blocks ≤ 61/123/185/247) and that header byte 0 bit 7 was "max FEC". Each was then **checked by our own tests against
  data, not code**: the FX.25 first root against a real off-air block (it decodes only with root 1), the IL2P layout and
  C-bit placement against the spec's example packets (our encoder reproduces all three byte for byte).

## How it works

### The 9600 receiver (`vibe_g3ruh.h`)

```
channel IQ (dial at DC, any rate ≥ 24 kS/s)                         discriminator audio (any rate, any polarity)
  → NCO (the AFC's correction)                                                   │
  → channel FIR ±6 kHz (stops by ±10 kHz), decimated to ≥ 32 kS/s               │
  → FM discriminator (±3 kHz = ±1) → click limiter (±1.6 about the eye)          │
  └──────────────────────────────→ exactly 48 kS/s (5 samples a bit) ←───────────┘
      → receive low-pass 5.4 kHz → the eye (peak / valley) → five slicers (centre ± 0.12, ± 0.24 of the half-eye)
      → each: its own bit clock → G3RUH descrambler → HDLC + FX.25 ; raw line bits → IL2P  → the merger → frames
```

- **SIMD:** every per-sample stage before the slicers is a vibedsp kernel (NEON on both ARMs, SSE2 on x86, scalar
  elsewhere — FirDecimator, FmDemod, RationalResampler, RealFir, NCO). The slicer bank is a per-sample state machine (a
  compare, a few adds, a branch per slicer, the clocks wrapping at different samples) where vector lanes do not pay; it is
  0.07 % of a Mac core for five slicers. RS / FX.25 / IL2P decoding runs per frame, not per sample.
- **The bit clock (`SymClock`) — the bug that mattered.** The shared `vibehdlc::BitClock` moves its phase by a fixed share
  of every crossing's error and *wraps the phase itself*: a crossing handled on the sample just after a wrap can push the
  phase below 0, which it wraps to 0.99 — and the next sample emits the same bit again. Measured on 40 000 random bits:
  **18 slips at 12 dB Eb/N0**, all one way; every slip ends a frame and every FX.25 / IL2P block after it. `SymClock`
  never wraps on a correction, weights a crossing by its steepness, ignores crossings within 0.1 bit of a bit centre and
  caps each correction at 0.06 bit: **0 slips** at 15 / 12 / 10 / 8 dB, line BER 0 at 12 dB, 9 × 10⁻⁴ at 10 dB,
  6.7 × 10⁻³ at 8 dB. ★ The 1200 / 300 Bd APRS modem and AIS still use `BitClock` — see "Decisions".
- **The AFC** (IQ only) moves the NCO a third of the way every 5.3 ms while a slicer is inside a frame AND a carrier is
  there (the channel's power 5 dB over its own floor, or an open eye), clamped to ±12 kHz. A carrier 6 kHz off is pulled
  in within the first frame's preamble; on two minutes of noise it stays at 0 Hz.
- **Click limiting:** near the FM threshold a 2π click is sixteen times the deviation in one sample; it is held to ±1.6.
- **The eye** recovers from a noise gap in time for the next preamble (release 1/500 a sample — 1/1000 lost one frame in
  48 after a gap at 44.1 kHz).
- Filter corners were measured, not guessed (`test-ax25hs --tune`): channel 6 kHz / receive 5.4 kHz was best of six.

### FX.25 (`vibe_fx25.h`)

On the NRZI-decoded (and, at 9600, descrambled) data bits — the HDLC deframer's own bits. A 64-bit register is matched
against the 11 tags (≤ 5 bits wrong); the next n bytes (LSb first) are the code block; RS decode; the AX.25 frame inside
is found by its flags, unstuffed and must pass its own FCS-16. FX.25 can therefore add no false frame: a chance tag
(~10⁻¹¹ a bit) would also need an RS decode and a 16-bit FCS. A frame the plain deframer already passed comes again from
FX.25 after its check bytes; the merger counts it (`fecDupes`) and passes it once.

### IL2P (`vibe_il2p.h`)

On the raw line bits (no NRZI; at 9600 *before* the G3RUH descrambler). The receiver tries the layout header byte 0 bit 7
names first, then the other (v0.6 sends 16 check bytes with the bit at 0; older senders used it for "max FEC" / baseline).
Bytes read on past the packet (for the CRC or the longer layout) go back to the sync search, so back-to-back packets with
no preamble are not lost. **No false frames on noise:** a 23-of-24 sync match comes every ~69 s per bit stream and a
2-check-byte header decodes ~6 % of random blocks, so: a trailing CRC that is PRESENT (four exact Hamming codewords —
random bytes are that 1 time in 65 536) must match; a frame without a verified CRC is accepted only when its header
needed no correction and every block is clean or "strong" (≥ 8 check bytes, short of the code's limit); Type 1
callsigns must be capitals / digits, left-justified; a Type 0 header must be all zero but its count. With the CRC
verified, everything the codes can fix is accepted. ★ The first rule let a header corrected once through when the payload
was strong — `--full` caught it: a GRBAlpha frame at 9 dB came out as from "OM9G0R" (two wrong header bytes "corrected"
into another valid header, ~1 in 17; the payload's strength says nothing about the header). Fixed; a regression of 400
frames with two wrong header bytes, CRC sent and not, gives 0 wrong.

### AUTO, the frame log, the satellite name

- **AUTO** (`packet: "auto"`) = 1200 on the listener's audio **and** 9600 on their channel IQ in one run, FX.25 and IL2P on
  both. The default where 9600 is live. Manual 1200 / 9600 have the FX.25 / IL2P switches (both on unless switched off);
  HF 300 has neither. 9600 has no TUNE key — it has no one channel.
- **The frame log:** `{"type":"aprs_frame","data":{age, from, to, path?, ctl ("UI", "I 3/5", "RR 2"…), pid?, fec
  ("ax25"|"fx25"|"il2p"), fixed?, crc?, sat?, len, hex (≤ 256 bytes), text (printable ASCII), aprs?}}`, every frame,
  a digipeated copy too (an APRS frame after its `aprs_packet`). `aprs_list` carries `fx25`, `il2p`, `fixed`, `other`,
  `auto`, and `log` (newest 40) to a joiner. A UI/F0 frame whose information is binary and of no APRS type is telemetry:
  frame log only, never a station. A non-APRS frame goes to the gallery's day log ("OM9GRB>CQ UI · GRBAlpha · FX.25 ·
  100 bytes: …").
- **Satellite names** (`vibe_sat_calls.h`): only callsigns with a public source — the ISS's (RS0ISS, NA1SS, DP0ISS,
  OR4ISS, IR0ISS) and GRBAlpha's OM9GRB (SatNOGS DB; re-entered). A digipeater in the path that marked the frame counts
  (a frame "via RS0ISS*" is named ISS). More are added with their source, never guessed.

### For the satellite engine (branch `v12-sat`)

Nothing here builds orbits. What the engine hands the decoder:

1. **Doppler-corrected channel IQ.** The engine corrects inside the listener's DDC (SATELLITE-ENGINE.md §4.1), so the
   channel IQ this decoder reads (`feedChannelIq` → `Run::feedIq`) already has the satellite near 0 Hz. The decoder then
   needs nothing else: its AFC takes up the residual (±12 kHz clamp, a third of the way every 5.3 ms while a frame is in,
   frozen between frames — it never chases noise; measured −4 / +2.5 / +6 kHz offsets: 19–20 of 20 frames). A residual
   ramp of the size the engine leaves (tens of Hz/s) is far inside what it follows within a frame.
2. **The satellite's name**, from the engine's own hook (merged 2026-11-19): the host's run asks
   `vibe::sat::decoderView(session)` per frame (this listener's lock, else the shared dial's) and, while `on`, puts
   `satName` on every frame — the right answer for every satellite not in `vibe_sat_calls.h`. No attach parameter, no
   second copy of the lock. The decoder never applies `modelHz`: the channel IQ already carries `inChannelHz`, and its
   AFC takes only the residual (the hook's "do not correct twice").
3. **Optional diagnostics:** `Run::afcHz()` (the residual the decoder found — a closed-loop trim the engine could read)
   and `VIBE_PKT_LOG=1` (the receiver's eye, AFC and counts every 5 s to stderr).

Satellites using other framings (CCSDS / AX100 / GOMspace, Geoscan, GFSK without G3RUH) are not decoded here.

## The protocol

- **hwinfo / vibeserver.json:** `"aprsFec":true` (this server's packet decoder reads FX.25 and IL2P); `"pkt9600":true` or
  `false` with `"pkt9600Why"` (greyed with the reason, e.g. "Outside this radio's locked range (88.0–96.0 MHz) — 9600
  packet is on 2 m (144–148 MHz) and 70 cm (420–450 MHz)"); **no `pkt9600` at all on an Icom** (its FM audio is
  demodulated in the radio; 9600 needs the channel IQ) or an older server. Nothing when APRS is switched off.
- **Attach:** `{"type":"audio_extension_attach","extension_name":"aprs","baud_rate":1200,"packet":"auto"}` ·
  `{… "baud_rate":9600,"packet":"9600","fx25":1,"il2p":0}` · `{… "baud_rate":300}`. `baud_rate` stays so an older server
  runs 1200 (or 300); `fx25` / `il2p` default to 1.
- **Server log:** `decoder attached: aprs AUTO (1200 + 9600) FX.25 on IL2P on` / `aprs 9600 Bd FX.25 off IL2P on`.

## Threading, memory, CPU

- The 9600 receiver runs on the decoder host's own thread (`vibe-decode`), fed from the host's channel-IQ queue (drop,
  never wait; 2 s at most). The DSP thread only copies — one relaxed atomic load per block when no packet decoder runs.
- Bounded: the merger holds one frame, the frame log 60 entries (≤ 256 hex bytes each), IL2P's buffer ≤ 1.1 kB, FX.25's ≤
  255 B, per slicer. A 9600 run is well under 1 MB.

| What (this Mac, M5 Pro, one core, -O2) | Cost |
|---|---|
| 9600, every receiver on, five slicers, IQ at 48 kS/s | 0.16–0.17 % |
| …IQ at 250 kS/s | 0.23 % |
| …discriminator audio at 48 kHz | 0.14–0.15 % |
| …one slicer, AX.25 only | 0.09 % |
| a real 764 s SatNOGS recording (audio, five slicers, all receivers) | 0.19 % (1.48 s) |
| 1200 AFSK, FX.25 + IL2P off / on | 0.075 % / 0.078–0.080 % |
| Pi 2 | not measured (expect ×15–25, ≈ 3–4 % of one core for 9600 AUTO) |

Benchmark row **`dec_aprs9600`** — the packet decoder in AUTO on 9600 bursts (plain, FX.25, IL2P) at 16 dB in real time,
inside the APRS switch, a decoder slot; gated to radios that reach 2 m / 70 cm (`Need::Pkt9600`, never an Icom). It was
compiled in the server build; **its figure has not been taken** (the benchmark was not run here).

## Decisions for Stuart

- **The 1200 / 300 Bd APRS modem and AIS use `vibehdlc::BitClock`, which slips on a correction across its wrap** (measured
  here at 9600; the same code). Fixing it there would likely gain 1200 APRS sensitivity, but changes AIS / APRS results
  that their docs tabulate — wanted as its own change, re-measured? (Not touched here.)
- **AUTO as the default** where 9600 is live (it costs ~0.1 % of a Mac core more than 1200 alone) — or keep 1200 the default?
- **HF IL2P** (300 Bd, the NinoTNC HF modes) and **unscrambled 9600 FSK** (some cubesats) are not built — wanted?
- The **gallery** logs every non-APRS frame (one line each, hex cut at 32 bytes) — a cubesat pass is a few hundred lines.
  Keep, or summarise per pass?
- The satellite-name table holds only sourced callsigns (ISS, GRBAlpha). Extend from SatNOGS DB entries one by one, or
  leave it to the satellite engine's `sat` hint?
