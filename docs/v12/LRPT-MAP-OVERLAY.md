# METEOR LRPT: the automatic MAP OUTLINE (V12, 2026-11-24)

Branch `meteor-overlay` (off `v12-experimental` 999fb2d8d, beta92). Stuart's goal: *"make vibesdr the premier meteor
receiver"*, item 1: coastlines, country borders and a latitude / longitude grid over every METEOR picture, placed from
our own data with **no user setup and no per-satellite offsets**, one toggle, and **no outline at all** when the pass
cannot be trusted.

**Headline.** On Stuart's own METEOR-M2-4 pass of 23 Nov 2026 (Pi 500, RTL-SDR V4 + YouLoop) the outline lands
**~6 px (~6–7 km) east of the true coast near nadir and ~6 px / ~2 rows (~9 km) off over Norway at 25–45° scan
angle** — the coast sits visibly on the coast at any normal viewing size (1.5 screen pixels on a phone). That is ONE
pass with land in it; the other usable pass (22 Nov) was all cloud. The remaining 6 px is a constant cross-track
offset that a 0.42° roll would remove — **not applied** (see §Residual: an unexplained constant is a fudge until a
second pass shows it is the same).

## How it works

| Where | What |
|---|---|
| `vibe_lrpt.h` | `Receiver::stripTimeMs(s)` — each 8-line strip keeps the packet time the SATELLITE stamped on its scan period (ms of day). `lastStampMs()` for the clock check. 3.2 KB. |
| `vibe_lrpt_geo.h` | the geometry (below): `Georef` — a row table from SGP4, pixel → lat/lon and lat/lon → pixel; `Candidate`. Light: only `vibe_sat_orbit.h`. |
| `vibe_lrpt_overlay.h` | the checks (`checkClock`, `chooseSatellite`) and `makeOverlay` → the JSON. |
| `vibe_lrpt_coast.h` | GENERATED by `scripts/gen-lrpt-coast.mjs` from Natural Earth (public domain): 1:10m coastline + minor islands (≥ 25 km²), 1:50m lakes ≥ 2000 km², 1:10m land borders; Douglas–Peucker 1 km, 1/180° byte deltas: 170 k points, **531 KB read-only in the binary** (paged from the file when a pass is drawn, never on the heap). Compiled in because the outline is made on every kind of server (phone, Lite, a Pi without the map pack). |
| `vibe_lrpt_run.h` | at a pass's end the outline goes with the pictures (`Picture::geoJson` / `geoWhy`); while the picture grows, `{"type":"lrpt_geo","data":…}` for the quarter-size preview at most every 20 s. Our clock is paired with the newest stamp whenever a strip lands. |
| `vibe_bgdecode.h` `LrptGalleryTap` | files the outline as its own small item (kind `lrptgeo`, JSON) and each picture of the pass names it (`"geo"`), or carries the reason (`"gw"`). **The PNG is the plain picture, unaltered.** |
| `vibe_lrpt_burn.h`, shim | `/vibeserver/gallery/file/<picture>.png?outline=1` = a copy with the outline burnt in, made on request (our own PNG decoder over `vibe_inflate.h`), named "… map outline.png". Nothing stored. **Server-side** so the web page and the app (iOS and Android — OPEN hands a URL to the phone) get the same picture from one implementation. |
| `vibe_sat_engine.h` | `lrptCandidates(pickNorad)` (every listed bird with an LRPT downlink and elements, the pick marked), `observer()`. |
| `src/utils/lrptOutline.ts` | the one client rule (app + web): `OUTLINE_DEFAULT_ON = false` (Stuart: *"map outline should be a toggle"*), "MAP OUTLINE: OFF / ON", remembered per viewer (`vibe.lrptOutline`), defensive parsing, the reason line, `lrptgeo` items never listed, DOWNLOAD following the switch. |
| app | `GalleryOverlay` (SVG over the picture, the key beside OPEN / SAVE, the reason line), `services/lrptOutlineLive.ts` (one store: the live outline + the switch, AsyncStorage), `DecoderImageCanvas` (Skia paths over the live picture, never over PREV), the keys in `DecoderPanel` and `SatellitePanel`. |
| web | the gallery viewer (`#galOutline`, `#galGeo` SVG with viewBox = the picture's pixels, `#galOutlineWhy`), the live picture (`#decOutline` + `#decGeo` inside `#decImgWrap`, so the SATELLITE box, which borrows that wrapper, has them too), `lrptOutlineDom.ts`. |

The switch is reachable by D-pad / keyboard like the other keys (a `.btn` in the viewer's key row on the web; a
touchable key in the app).

## The geometry

Sources: WMO OSCAR "MSU-MR" (cross-track scanner, 2800 km swath, 1 km IFOV, six 1-km lines a second);
Spaceflight101 / eoPortal (scanning angle 54°, 2800 km); the instrument makers' paper (2950 km field of view); CCSDS
for the packet time. **No GPL code was read.** Everything else was measured on the passes.

1. **Line time.** Row r of the picture is in strip ⌊r/8⌋; the strips' stamps are fitted with ONE straight line
   (stamp = a + b·strip; b came out 1231.14 ms on both passes, i.e. 6.50 lines a second, residuals ≤ 0.5 ms), and row r
   is at `a + b·(r/8)` — so a missing strip still has a time, and a jumping stamp is caught. The day comes from OUR clock.
   **The stamps are UTC on METEOR-M2-4** (stamp 14:06:45.1 decoded at 14:06:46.5 by our clock: −1.4 s on 23 Nov, −1.6 s on
   22 Nov — the on-board buffer plus our 2 s IQ queue). The stamp marks the period's FIRST line: a ±0.5 s change moves
   everything ±3.2 rows and the near-nadir coast sits at −0.3…+0.9 rows with none.
2. **Where the satellite was.** Our SGP4 (WGS-72, as the elements are fitted) at each row's time, TEME → Earth-fixed by
   GMST (as `look()`); one SGP4 call a row.
3. **Which way it looks.** The orbital frame: **z down the WGS-84 ellipsoid normal under the satellite (geodetic
   nadir)**, y = z × v with v the INERTIAL velocity (across the track), x = y × z. Pixel c looks at angle
   θ = −(c + ½ − 784) · Δθ in the y–z plane (equal steps of angle: a rotating-mirror scanner), Δθ = 2 · 55.2° / 1568.
   **Column 0 is the satellite's right** (east on a northbound pass; the picture's top is its first line, so a northbound
   picture is south-up with east on the left — the other sign mirrors Scotland).
4. **The ground.** The ray meets the WGS-84 ellipsoid → lat / lon (Bowring). For the OUTLINE the inverse: each coast
   vertex's row is where it crosses the scan plane ((P − p)·x = 0, binary search over the row table, linear between
   rows), its column from the angle of P − p in the y–z plane; a vertex behind the Earth, past the scan's edge or before /
   after the picture is dropped and the line broken there. Lines are densified to 0.05° (the scan's curvature over a
   long straight coast) and thinned to 1 px.

Round trip pixel → ground → pixel: ≤ 0.05 px over the whole picture (`test-lrpt-geo`). The nadir column is the
sub-satellite point to < 0.5 km; the swath 2750–3000 km; a pixel 0.95–1.25 km at nadir; lines 1.05 km apart.

## The checks (fail closed, with a reason)

| check | refuses with |
|---|---|
| ≥ 3 strips heard | "too little of the pass to place it on the map" |
| the period 1225–1238 ms | "the satellite's line times step N ms, not MSU-MR's 1231 ms" |
| every stamp within 8 ms of the line | "the satellite's line times jump (one is N ms off the rest)" |
| the stamps within **5 s** of OUR clock when they arrived | "the satellite's clock reads 3 h 0 min ahead of ours" (METEOR-M2 3, Oct 2023, sent wrong on-board times — this is that case) |
| elements ≤ 5 days from the pass | "the orbit data is more than 5 days old" |
| a METEOR above our horizon at the picture's middle (the pick first; two up and no pick, or no location and two candidates = refused) | "no METEOR satellite was above this server's horizon…", "two METEOR satellites were up at once…", "this server's location is not set…" |

5 s, not more: a stamp error of a few seconds is ~7 km a second along the track. The real skew is −1.4 / −1.6 s.

**The residual** — normalised cross-correlation of the picture against the land the model predicts (Natural Earth 10m
land rasterised at 0.01°, `scripts/lrpt_geo_ncc.py`), in boxes; +dx = the real coast is to the RIGHT of the outline,
+dy = LATER rows. Channel 4 (3.8 µm: land cold, very clean edges at a 5° sun) and channel 2 (0.9 µm) agree to ~1–2 px.

| model (ch 4 / ch 2) | Norway, cols 150–450 (θ 23–44° east) | Scotland, cols 700–900 (nadir) |
|---|---|---|
| published 54.4°, geocentric nadir | dx +12.8 / +11.0, dy +4.0 / +4.6 | dx +5.1 / +4.8, dy +2.0 / +2.4 |
| 54.4°, **geodetic** nadir | dx +13.4 / +11.9, dy +2.2 / +2.2 | dx +6.0 / +5.5, dy −0.2 / +0.4 |
| **55.2°, geodetic (shipped)** | **dx +6.2 / +4.6, dy +2.3 / +2.1** | **dx +6.7 / +5.7, dy −0.3 / +0.3** |
| …a second Scotland box (rows 520–620) | | dx +8.5 / +6.7, dy +0.7 / +0.8 |
| 55.6° (the makers' 2950 km) | dx +2.6 / +1.1 | dx +7.0 / +5.7 |

Pixel sizes: ~1.1 km at nadir, ~1.5 km across at 35°. So **~6–7 km at nadir, ~9 km on Norway's coast**.

**Sanity sweeps (ch 4, the shipped model)** — what a constant would do, to see what the data asks for:

| change | Norway dx / dy | Scotland dx / dy |
|---|---|---|
| none | +6.2 / +2.3 | +6.7 / −0.3 |
| time −0.5 s / +0.5 s | +6.2 / −0.9 · +6.3 / +5.5 | +6.8 / −3.5 · +6.6 / +3.1 |
| roll +0.5° / −0.5° | −0.8 / +2.2 · +13.3 / +2.4 | 0.0 / −0.1 · +14.0 / −0.6 |
| pitch +0.5° / −0.5° | +6.1 / +9.2 · +6.3 / −4.9 | +6.3 / +6.7 · +7.1 / −7.4 |
| yaw +0.5° / −0.5° | +6.4 / −2.8 · +6.1 / +7.4 | +6.7 / −0.1 · +6.8 / −0.4 |
| roll +0.42° + yaw +0.25° | +0.3 / −0.3 | +0.8 / −0.1 |

Read: the TIME is right (a time error moves both regions alike; there is none at nadir). The along-track error at
nadir was the GEOCENTRIC frame (2.3 rows ≈ h · 0.19°, the angle between the geocentric and geodetic verticals at 57°N —
the satellite points along the ellipsoid normal), which is physics, so it is in. The scan width: the published figures
bracket 54.4°–55.6°; the coast fit puts it at ~55.2°, inside the bracket — an instrument constant for every MSU-MR,
in. What is left is a constant ~6 px across the track (0.42° of roll) and a small yaw (0.25°: 2 rows at 500 px off
nadir). Those are exactly the per-satellite "Alfa / Delta" values other tools ask their users to type in — an attitude /
mounting bias of the spacecraft or the instrument. **They are NOT applied**: one pass cannot say whether they are the
same on the next pass, on a southbound pass, or on M2-3. With them the residual on this pass is under 1 px.

**Cost.** `makeOverlay` for an 800-row picture: 3.2 ms on the M5 (`test-lrpt-geo`) — on a Pi 2 perhaps 20–30× that,
~0.1 s, once at a pass's end and once every 20 s while a picture grows (the decode thread). The burnt-in copy decodes
and re-encodes the PNG on request: ~4 MB of pixels for a 900-row pass.

## Not done / open

- **Only one pass with land.** A second clear pass — ideally SOUTHBOUND (an evening M2-3/M2-4 pass), and one from M2-3 —
  would show whether the 0.42° roll / 0.25° yaw is a constant of the spacecraft (then it belongs in the satellite's
  sats.json entry as published attitude, not as a user setting) or something in our model. Run
  `tool-lrpt-geo <capture> --sats sats.json` then `tool-lrpt-geo-fit … mask` + `lrpt_geo_ncc.py` on the land boxes.
- **The 80k mode and M2-3's timestamps** are unproven here (no decodable capture). If M2-3 stamps Moscow time (+3 h) the
  check refuses with "3 h 0 min ahead" — the honest answer until we know which it is.
- **Backfill** of pictures saved before this: not possible as saved. The gallery keeps the PNG and the time the
  DECODER STARTED, not the strips' stamps, and a few seconds is tens of km. From now on the outline JSON keeps the pass's
  start / end / period / satellite, so a later re-render (newer orbit, a better model) is possible for new passes; a pass
  that failed its checks keeps only the reason (the stamps could be kept too if Stuart wants a "retry" later).
- **R36S handheld**: not done (its native UI draws the SSTV-shaped preview; the outline JSON is there for it).
- **VFO B's picture** in the SATELLITE box has no outline (its decoder client is kept out of the live store).
- Auto-registration against the picture itself (the cross-correlation above, run on the server) could remove the last
  few km on clear passes — not done: a cloudy pass could fool it, and that is a wrong outline.
